# TS-060 | Qualifier la continuité UX du pilote React sur le détail projet

## User value

Pouvoir utiliser le détail projet migré en React sur ordinateur et Android sans perdre le focus, les brouillons, les données visibles ou la confiance dans la synchronisation. Établir une décision explicite de poursuite avant de migrer d'autres surfaces.

## Verified context

- TS-058 et TS-059 ont été fusionnées, la CI et Pages sont vertes ; seul `#/sujet/<id>` est rendu par React. Le [bilan TS-059](../../docs/product/react-project-detail-pilot.md) donne un GO **technique limité**, sans recette Android/Dexie Cloud réelle.
- La référence transversale [Notion UI-10](https://app.notion.com/p/40212ac916368193be78d23b6d012bb5) impose des preuves à chaque lot : continuité, transitions de lecture, Undo 10 s et protection des caches. TS-049/050/052 et `openspec/specs/ux-interaction-continuity/spec.md` définissent les comportements déjà attendus.
- Ce lot est une qualification et un durcissement **bornés** du pilote, pas une généralisation de React.

## Scope

1. Formaliser une matrice de recette reproductible pour le détail projet React : création, édition et annulation, sous-tâches, filtres, priorités, menus, glisser-déposer et alternative clavier, retrait/Undo, listes longues, retour/avant et rechargement.
2. Compléter les tests déterministes et d'intégration sur données synthétiques pour les chemins non couverts : un seul handler et une seule commande, focus/scroll et clavier virtuel, parent développé, brouillon non sauvegardé, identité/espace changés, projet disparu, lecture Dexie bloquée et rafraîchissements inter-onglets. Les tests doivent vérifier l'invalidation des anciennes données visibles.
3. Préserver les états Overview définis par TS-052 : loader discret après 250 ms, attente durable après 8 000 ms, pas de flash de diagnostic ni de faux état vide. La tâche peut tester ces contrats, sans refondre Overview ni le moteur Dexie.
4. Corriger seulement les régressions démontrées **dans la frontière React ou ses commandes** et maintenir l'adaptateur en lecture seule, les écritures métier uniques et les règles de `site/core.js`. Toute correction d'identité, de synchronisation ou de migration Cloud sort de ce lot et nécessite une tâche spécifique.
5. Produire un compte rendu vérifiable : scénarios automatisés effectivement passés, scénarios physiques observés ou non exécutés, limites, mesures de bundle et décision humaine GO/NO-GO pour le **lot suivant**. Une exécution CI ne prétend pas remplacer les essais sur appareil.

## Acceptance criteria

- [ ] Les tests synthétiques prouvent l'absence de double callback/écriture, de mutation sur montage/démontage, de fuite de contenu de l'ancienne identité et de perte d'état transitoire hors exceptions spécifiées.
- [ ] Les opérations du détail conservent les règles de priorité, ordre, parent/sous-tâche, notes brutes, titres, compteurs, Undo 10 s et commandes clavier.
- [ ] Les transitions de navigation, de projet, de compte et de lecture bloquée démontent la racine React avant tout retour au rendu vanilla ; aucune requête Cloud ou écriture IndexedDB supplémentaire n'est créée.
- [ ] La matrice de recette distingue explicitement tests automatisés, essai navigateur isolé, Android réel, clavier, tactile, lecteur d'écran selon disponibilité et Dexie Cloud **de test**, en indiquant pour chacun les preuves ou `NOT_RUN`.
- [ ] Le bilan de qualification compare les résultats au pilote TS-059 et consigne une recommandation GO/NO-GO, sans attribuer un GO global à une simple CI verte.
- [ ] `npm run check`, `npm run build`, `npm run verify:build` et les tests React ciblés passent sur la branche proposée.

## Implementation constraints

- Préserver `site/core.js`, les données locales, les identifiants, la configuration Cloud/OTP, la CSP et `/threadstep/`. Ne pas introduire de second store, effectuer de reset de cache ni effacer/réimporter des données personnelles.
- Utiliser uniquement des données synthétiques et un environnement Cloud de test pour les tests automatisés. La recette sur appareils personnels doit être **non destructive**, avec sauvegarde préalable pour tout scénario sensible ; les étapes à réaliser par le propriétaire figurent sous `Manual acceptance`, non comme cases imposées à `apply`.
- Tout problème observé de synchro hors React doit être documenté et aiguillé vers le backlog de fiabilité Dexie, sans extension opportuniste du périmètre.
- `automation: manual` et `risk: medium` : une validation utilisateur des scénarios physiques et de la décision de généralisation est nécessaire.

## Manual acceptance

Sur ordinateur puis Chrome Android avec des projets de test : ouvrir le détail, créer/modifier/compléter des tâches, réordonner au tactile et au clavier, ouvrir/replier une longue liste, utiliser menus et Undo, naviguer vers Overview et revenir, tester le clavier virtuel et le scroll. Sur une instance Dexie Cloud de test seulement : rafraîchissement depuis un second appareil/onglet et changement de compte/espace. Documenter `PASS`, `FAIL` ou `NOT_RUN` pour chaque scénario, sans purge ni restauration risquée sur les données personnelles.

## Post-sync review

Vérifier les spécifications OpenSpec, la CI indépendante sur le SHA de PR, la CI et Pages après fusion, puis compléter la recette physique distinctement. Obtenir une décision de poursuite avant toute application TS-061/TS-063, sans lancer automatiquement une autre tâche.

## Out of scope

Refonte Stitch, design system, Tailwind, migration d'Overview ou navigation, modification des règles métier, traitement profond du moteur Dexie Cloud, nouvel import/export, suppression de caches, changement de workflows ASF.

## Assumptions or decisions

- Les défauts de qualification peuvent conduire à un NO-GO et à des tâches correctives distinctes. Le GO technique TS-059 ne suffit pas à autoriser l'étape suivante.
- Les observations Android et Dexie réelles nécessitent l'intervention humaine du propriétaire ; leur absence doit être signalée, jamais inventée.
