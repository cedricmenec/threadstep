## Objectif

Déployer **sur une branche de qualification uniquement** un modèle de persistance Git CAS d'**une** admission V3, avec un justificatif signé, sans autoriser les workflows ni les paiements. Garantir qu'une deuxième admission, un SHA de tête divergent ou une réponse GitHub perdue n'autorisent aucun départ supplémentaire.

## Frontière de sécurité et restrictions

Le prototype n'intègre **aucune clé publique de production**. Le paramètre \`verificationKey\` doit provenir d'une politique de sécurité **owner-approved**, immuable pour un run et sous contrôle du code de confiance. **Une clé fournie dans des inputs de workflow, par le manifeste, par le modèle ou par une branche non fiable rendrait la vérification inutile**. Les signatures générées dans les tests sont des exemples synthétiques, pas des mandats utilisateur.

Le reçu signé prouve uniquement la possession de la clé privée ; il ne prouve pas automatiquement que l'issuer a vérifié \`workflow_dispatch\`, le propriétaire réel, la bonne branche et SHA, le runAttempt=1, la liste des tâches, ni l'initialisation légitime. Ces vérifications doivent être réalisées **avant signature**, par un publisher distinct et approuvé. Les erreurs de vérification sont bloquantes.

La machine V3-007 permet une clôture nominale et une quarantaine, mais **cette PR n'écrit que ADMIT** ; aucune API de RELEASE, de sortie de quarantaine ou de récupération ne peut être appelée automatiquement. Un CAS du ref global **ne sérialise pas** les paiements V1 : conserver le groupe \`threadstep-paid-development-v1\`, une réservation unique et les preflights payants.

Aucune modification de main, de \`.github/workflows\`, secrets, permissions, \`AGENTS.md\`, aucun run OpenRouter, dispatch, ajout de clé App, ni merge.

## Qualification CI de PR empilée

La CI existante est déclenchée par `pull_request` seulement lorsque la branche de destination est `main`. Pour vérifier cette PR empilée, sa destination est temporairement `main` le temps d'un commit documentaire de qualification et du job `check`, puis restaurée à `feat/asf-v3-007-admission-interlock`. Ce changement de métadonnée de PR ne constitue ni une fusion, ni une modification de workflow, ni une autorisation de déploiement.


## Durcissement de la traçabilité de l'autorisation

- [x] Écrire en **une seule création d'arbre Git** \`registry.json\` et \`admission-evidence/<waveId>.json\` (permis Ed25519 complet), sans réécriture de fichiers de vague ni de workflow.
- [x] Ajouter \`scripts/asf/v3/signed-global-witness.mjs\` : à chaque lecture, rejouer le registre puis revérifier **chaque événement ADMIT historique** contre une pièce signée lue **au même SHA de commit Git**. Vérification de type, chemin, taille, UTF-8, base64 et signature.
- [x] Le port \`observeGlobalAdmissionSnapshot\` requiert une clé de vérification et refuse un historique admis qui manque de preuve ou présente une signature divergente. Les réponses de lecture n'autorisent toujours pas le paiement.
- [x] Tests de falsification : registre structurellement rejouable mais admission non signée, témoin manquant, fausse clé, signature modifiée après un PATCH reçu, chemin de témoin invalide.
- [ ] Faire revoir la **confiance d'origine de la clé publique**, qui reste volontairement **non configurée** : la vérification d'une signature avec une clé choisie par l'appelant ne prouve PAS le mandat du propriétaire.
- [ ] Exiger en déploiement une protection indépendante contre la réécriture des refs/témoins et un émetteur ne remettant son justificatif qu'après contrôle réel du run propriétaire.

**Découverte de la revue :** avant ce durcissement, \`replayAdmissionRegistry\` pouvait accepter un événement \`ADMIT\` correctement formé mais sans signature conservée. Cela démontrait une cohérence de journal, pas une approbation. Le durcissement ferme la lacune de **traçabilité cryptographique du témoin**, mais la validation du propriétaire et la protection Git restent P0.

Qualification du durcissement : CI `pull_request` existante lancée temporairement depuis la base `main`, puis base de revue #75 restaurée après succès. Aucun changement de YAML ou permissions.

- [x] Régression P0 supplémentaire : un registre contenant une libération `RELEASE` même structurellement valide mais **sans protocole d'attestation** est rejeté par l'audit des témoins. Événements `QUARANTINE` et `DIAGNOSTIC_NOTE` également non autorisés par cet audit jusqu'à conception d'une preuve distincte.
