## But utilisateur

Une signature Ed25519 sur \`ADMIT\` ne protège pas, à elle seule, contre le remplacement du ref global par une autre chaîne Git ni contre le retour vers un registre antérieur. L'objectif de ce lot est de **comparer la vraie branche et ses commits Git à une genèse et un checkpoint approuvés indépendamment**, avant d'afficher une quelconque preuve de cohérence. Le code n'accorde **aucun droit** à un modèle ou à un dispatcher.

## Précautions P0

\`trustedAnchor\` est injectable **uniquement pour tests et composants de confiance futurs**. Une ancre fournie par le modèle, un manifest, un fichier que l'agent peut écrire, une PR de feature ou un input \`workflow_dispatch\` n'a aucune valeur d'authentification. Dans ces situations, un acteur peut fournir sa propre clé, son propre commit genèse et ses propres témoins et obtenir une **cohérence apparente**.

Le registre global de ce prototype ne prévoit qu'un ADMIT. Cela limite volontairement l'historique validé à un seul enfant de genèse, de sorte qu'une seconde vague **n'est jamais libérée automatiquement** ; cela ne constitue pas encore le protocole complet 1..10 ni une coordination V1/V3 live.

Une API GET stable peut être obsolète dès la réponse : le résultat est une observation **non autorisante**, et non une primitive d'acquisition de verrou. La seule admission concurrente doit passer par CAS Git sur le ref et le vérificateur indépendant de #77. Le contrôle du propriétaire reste non implémenté comme racine de confiance ; #79 vérifie des valeurs cohérentes sans autoriser l'émission.

Pas de workflow, permission, secret, clé réelle, branche opérationnelle, dispatch, OpenRouter, merge ni changement de main.
