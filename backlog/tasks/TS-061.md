# TS-061 | Introduire un socle de composants React et des tokens CSS sémantiques

## User value

Faire évoluer les vues ThreadStep avec des composants cohérents, accessibles et réutilisables, tout en préservant l'interface et les interactions déjà familières. Réduire le coût des lots responsive futurs sans imposer une refonte globale.

## Verified context

- Le pilote TS-059 dispose de composants `site/project-detail/*.jsx` reliés à un adaptateur et à des commandes métier existantes ; Overview et Paramètres sont encore vanilla.
- Le [cadrage UI-03](https://app.notion.com/p/40212ac91636810da4f8ca67cddc3111) décrit tokens, variantes et accessibilité. Tailwind n'est pas une dépendance technique de React et aucun choix Tailwind n'est actuellement approuvé.
- La progression maîtrisée retient pour ce lot **du CSS sémantique compilé localement**, sans changement général de rendu. Un éventuel arbitrage Tailwind reste une décision produit ultérieure.

## Scope

1. Définir des tokens CSS sémantiques versionnés pour couleur, typographie, espacement, rayons, focus, erreur, état désactivé et responsive. Mapper les valeurs existantes autant que possible afin de préserver la parité graphique.
2. Introduire dans un emplacement partagé de petits composants React de présentation (par exemple bouton, badge de priorité, champ/formulaire et déclencheur de menu), avec interfaces de props explicites, variantes documentées et libellés accessibles. Le nombre exact doit rester limité aux éléments réellement réutilisés dans le pilote.
3. Réutiliser au moins deux primitives dans la surface React du détail projet pour démontrer l'absence de divergence et de duplication, sans migrer Overview ni changer la propriété DOM du contrôleur.
4. Documenter les conventions de composant, tokens, styles, états et intégration progressive des maquettes validées. Les éléments vanilla peuvent réutiliser les mêmes variables CSS sans imposer React à leurs routes.
5. Ajouter des tests de rendu/états/interaction et de non-régression visuelle ou structurelle sur des tailles représentatives, ainsi que les contrôles d'accessibilité automatisables.

## Acceptance criteria

- [ ] Les tokens sont sémantiques, centralisés, documentés et embarqués dans le build Vite ; aucune police, bibliothèque d'icônes ou feuille CSS distante n'est requise à l'exécution.
- [ ] Les primitives exposent leurs variantes/états (focus visible, disabled, erreur, priorités) sans recopier des règles métier ni appeler Dexie, OTP ou `persist()`.
- [ ] Au moins deux primitives servent effectivement dans le détail React, avec des tests de composants et une parité de classes, libellés, comportement et ordre de lecture.
- [ ] Les objectifs d'accessibilité sont explicités et contrôlés lorsque possible : contraste texte 4,5:1, focus/éléments non textuels 3:1, cibles tactiles visées à 44 px et navigation clavier. Les exceptions justifiées restent visibles dans le bilan.
- [ ] Le fonctionnement à 320, 390, 430, 768 et 1280 px ne présente pas de débordement introduit par les primitives. Le CSS et la CSP restent compatibles avec Pages `/threadstep/`.
- [ ] `npm run check`, `npm run build`, `npm run verify:build` et les tests ciblés passent, sans nouvelle écriture métier, doublon de gestionnaire ni changement de stockage.

## Implementation constraints

- La décision de poursuite de TS-060 doit être favorable avant de modifier la surface React livrée. En cas de NO-GO, arrêter l'application de cette tâche et faire traiter la régression.
- Préserver `site/react-adapter.js`, les contrôles de propriété DOM et les commandes du contrôleur. Les primitives restent des composants de présentation réutilisables, pas un nouveau state manager ou routeur.
- Conserver par défaut les couleurs, styles et classes utilisateurs actuels. Toute différence graphique sensible exige une décision spécifique ; cette fiche n'autorise pas la conversion de l'application en Stitch.
- Les bibliothèques tierces, Tailwind et les CDN ne sont pas nécessaires au périmètre. `automation: manual` et `risk: medium` protègent la parité du pilote et les choix de conception transversaux.

## Manual acceptance

Comparer le détail projet avant/après sur ordinateur et Chrome Android : menus, boutons, labels et priorités, contrôles d'édition, zoom/tailles cibles et focus. Vérifier l'absence de différence fonctionnelle, l'Undo, le scroll et le tactile. Consigner les exceptions d'accessibilité nécessitant une vérification manuelle.

## Post-sync review

Comparer les classes, CSS compilé et poids du build, puis vérifier CI sur le SHA exact, Pages et la recette humaine. Ne pas convertir automatiquement les autres vues après la livraison de ce socle.

## Out of scope

Tailwind, kit visuel Stitch intégral, nouvelles couleurs, refonte d'Overview, navigation responsive, réécriture des formulaires Cloud, migration des données, nouveau routeur, nouvelle logique de synchronisation ou de sauvegarde.

## Assumptions or decisions

- Le choix du CSS sémantique local est une décision de **périmètre pour ce premier lot**, pas une interdiction future de Tailwind.
- Les composants exacts seront choisis d'après les duplications réellement observées ; ne pas constituer une bibliothèque abstraite sans consommateurs.
