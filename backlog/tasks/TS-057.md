# TS-057 | Introduire Vite sans modifier le comportement de ThreadStep

## User value

Disposer d'un serveur de développement et d'un build statique reproductible pour préparer des composants UI réutilisables, sans imposer React ni modifier l'expérience utilisateur actuelle. La migration d'outillage ne doit ni perturber les données IndexedDB/Dexie Cloud, ni modifier les opérations sensibles de l'application.

## Contexte vérifié

- Sur `main` au 23 octobre 2026, le document d'entrée est `site/index.html`, les modules et styles sont servis depuis `site/`, et `package.json` ne déclare ni Vite ni scripts `dev`, `build`, `preview`.
- `tools/build-vendor.mjs` produit avec esbuild le module `site/vendor/dexie-cloud.mjs`, chargé localement. Les versions Dexie sont épinglées et l'application applique une CSP stricte.
- `.github/workflows/pages.yml` publie directement `site/` sans étape de build. Ce workflow est protégé par `AGENTS.md` et ne peut être modifié dans une PR produit ordinaire.
- Cadrage Notion UI-01 : [Intégrer Vite à comportement constant](https://app.notion.com/p/40212ac916368102ab70ee8bfaa1ae7d). Les maquettes Stitch ne constituent pas un contrat d'intégration graphique dans cette tâche.

## Scope

1. Ajouter Vite comme dépendance de développement **à version exacte** avec lockfile cohérent ; exposer les commandes `npm run dev`, `npm run build` et `npm run preview`. Conserver `npm run check` et les commandes existantes.
2. Définir clairement `site/` comme source de l'application et un répertoire de sortie statique **distinct** pour la compilation. Empêcher l'écrasement du code source et l'inclusion accidentelle de fichiers de développement, secrets, tests ou artefacts internes dans le site construit.
3. Configurer la base de publication GitHub Pages `/threadstep/` et la résolution des chemins des scripts ES modules, styles, icône, ressources et vendor Dexie. Les liens de navigation par fragment (`#/`, `#/parametres`, etc.) doivent rester fonctionnels au chargement direct et au rafraîchissement.
4. Conserver le code applicatif vanilla et ses frontières : modules métier, stockage local, synchronisation facultative Dexie Cloud, consentement, authentification OTP, isolation des comptes, sauvegardes, imports/fusion et restaurations. Ne pas introduire de nouvelle requête, migration de données ou initialisation Cloud par l'outillage.
5. Préserver la politique CSP effective en production et le chargement local des dépendances. Documenter et tester séparément les contraintes spécifiques du serveur Vite (notamment HMR) sans affaiblir les protections du site publié.
6. Choisir et documenter une stratégie déterministe pour `site/vendor/dexie-cloud.mjs` (prébundle conservé ou pipeline équivalent), sans doublon de Dexie ni dépendance à un CDN runtime. Garantir l'ordre de chargement et les chemins dans l'artefact construit.
7. Ajouter une vérification reproductible du contenu de build et une recette de `preview` sous `/threadstep/`. Documenter commandes locales, diagnostic des chemins cassés et procédure de retour arrière vers la publication statique actuelle.
8. Préparer explicitement le passage ultérieur du déploiement Pages à l'artefact construit, **sans modifier `.github/workflows/*` dans cette tâche produit**. La bascule effective demande une tâche documentaire ASF distincte, une autorisation spécifique, une PR dédiée et la validation de ses contrôles.

## Acceptance criteria

- [ ] `npm ci`, `npm run dev`, `npm run build` et `npm run preview` fonctionnent avec des versions épinglées ; deux builds identiques donnent une arborescence et un contenu attendus, hors métadonnées éventuellement documentées.
- [ ] L'artefact statique est isolé de `site/`, n'expose aucun fichier sensible et toutes les ressources restent accessibles via le préfixe `/threadstep/`, sans URL absolue accidentelle à la racine du domaine.
- [ ] La navigation Overview, détail de projet et Paramètres par hash, y compris retour, rechargement et accès direct, reste inchangée dans le site construit. Les états vides, de chargement et d'erreur ne changent pas.
- [ ] Le chargement du bundle Dexie n'introduit aucun doublon d'instance ou échec de résolution des modules ; aucun CDN tiers runtime, secret ou script inline non autorisé n'est introduit.
- [ ] Sur une base locale existante, les projets, tâches et sous-tâches persistent après build/refresh et navigation ; aucune migration, suppression ou changement d'identité IndexedDB n'est déclenché par Vite.
- [ ] Les parcours critiques import JSON, export JSON, prévisualisation et consentement avant restauration, ainsi que configuration Cloud, OTP, état de synchronisation et isolation des comptes, conservent leurs gardes existantes. Les vérifications Cloud sont réalisées sur un environnement de test et sans transfert implicite.
- [ ] La CSP de la version construite reste restrictive ; le serveur de développement fonctionne sans nécessiter d'assouplissement de la CSP de production. Les tests de chemin, de chargement et de non-régression sont automatisés autant que possible.
- [ ] `npm run check` reste vert ; les tests propres au build sont exécutés et les limitations de validation navigateur sont explicitement signalées.
- [ ] `site/` continue d'être publiable **sans changement de Pages dans ce lot** ; le guide distingue clairement l'artefact Vite validé localement du site réellement en production.

## Implementation constraints

- Privilégier un changement d'outillage, d'assets et de documentation ciblé. Aucun nouveau framework ni réécriture des moteurs métier n'est nécessaire.
- Ne pas modifier `AGENTS.md`, `.github/workflows/`, `opencode.json`, les secrets, permissions GitHub ou les mécanismes de sécurité ASF depuis cette tâche produit. Toute évolution du déploiement se fait dans une tâche/PR ASF explicitement autorisée.
- Ne pas renommer les noms de bases IndexedDB, les URLs Dexie, les routes publiques ou les formats de sauvegarde. Éviter toute mise à jour silencieuse de dépendances métier.
- Préserver la compatibilité desktop/Chrome Android, clavier et lecteur d'écran ; aucune modification cosmétique ou comportementale n'est attendue.

## Manual acceptance

Comparer sur desktop et Chrome Android la version statique actuelle et le build Vite servi sous `/threadstep/` : ouverture d'Overview, navigation, tâches/sous-tâches, scroll/focus, hors ligne et refresh. Vérifier sur **données de test** les imports/exports, une restauration annulée, la configuration Cloud et les transitions OTP/session sans autoriser de purge réelle. Contrôler les ressources dans les outils réseau et l'absence d'erreur CSP.

## Post-sync review

Vérifier le diff OpenSpec et les ressources embarquées, exécuter le build et les tests sur le SHA final, contrôler la CI indépendante et conserver l'ancien chemin Pages tant que la tâche ASF de bascule de publication n'est pas explicitement autorisée et validée. Ne pas annoncer que Pages sert déjà le build Vite sur la seule base de la présente tâche.

## Out of scope

React, Tailwind, refonte graphique, composants Stitch, nouvelle navigation, changement de fonctionnement Dexie, migration des données, nouvelles fonctionnalités, modification du workflow CI/Pages et bascule effective en production de l'artefact Vite.

## Assumptions or decisions

- Décision de découpage : livrer d'abord un **build Vite vérifié sans modification du déploiement** ; prévoir ensuite la bascule GitHub Pages via une tâche ASF distincte. Le site publié reste le site statique existant jusqu'à cette décision.
- `risk: medium` et `automation: manual` en raison des risques de chemins, CSP, bundling Dexie et divergence entre version construite et publiée. `ready` décrit uniquement la préparation documentaire de cette étape.
- Aucun lancement OpenSpec/OpenRouter ni aucune modification de code n'est autorisé par cette fiche seule.
