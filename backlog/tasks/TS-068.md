# TS-068 | Harmoniser les cartes projet et tâche avec Stitch

## User value
Rendre les cartes de projets d’Overview et les cartes de tâches du détail projet plus cohérentes avec les références Stitch approuvées, tout en gardant les usages actuels lisibles et fiables sur mobile et desktop.

## Scope
- Harmoniser la composition, la hiérarchie typographique, les couleurs, les espacements, les surfaces, les bordures et les indicateurs des cartes projet d’Overview et des tâches dans la vue projet.
- Utiliser comme références le desktop « Mes Projets - Vue d'ensemble », le desktop « Projet - Détail et Gestion des Tâches », les références mobiles M01 « Mes projets / Overview » et M05 « Détail d'un projet », ainsi que les composants M32 utiles.
- Conserver les données et commandes déjà livrées : titre, compteurs, progression canonique, aperçus de tâches, notes, priorités, achèvement, sous-tâches, reprise, ouverture et réordonnancement existants.
- Réutiliser les composants et tokens existants, en particulier `ProjectCard`, `OverviewTaskList`, `TaskItem`, `ProjectDetail` et `site/styles/tokens.css`. Préférer des ajustements CSS et JSX locaux ; ne créer ni nouvelle dépendance, ni abstraction ou couche générale.
- Actualiser les spécifications canoniques de présentation touchées par le changement. Ne modifier une décision d’architecture que si une contradiction réelle avec le code ou les spécifications l’exige.
- Avant de passer cette fiche à `ready`, préciser pour chaque groupe de propositions Stitch absent du produit si on l’exclut des cartes, si on en fait une tâche fonctionnelle distincte, ou si un élément statique/désactivé est souhaité. Aucun choix ne découle de cette fiche.

## Acceptance criteria
- [ ] Les cartes projet Overview et les cartes de tâches du détail adoptent une hiérarchie visuelle cohérente avec les références retenues, sans effacer la distinction structurelle entre tâche parente et sous-tâche.
- [ ] Le rendu s’adapte à 320, 390, 430, 768 et 1280 px sans débordement horizontal, contenu rogné ni perte de commandes existantes.
- [ ] Chaque compteur et indicateur reste calculé à partir des données canoniques existantes ; aucune valeur de démonstration ou donnée de projet fictive n’est introduite.
- [ ] Les commandes, routes, données, règles métier, priorités, persistance et états de synchronisation restent inchangés. Les brouillons, le focus, le scroll, l’ordre de lecture, les interactions et les propriétaires DOM actuels restent continus.
- [ ] Les fonctions nouvelles ne sont ajoutées que si elles ont fait l’objet d’une décision produit et d’un cadrage fonctionnel séparé. Les éventuels éléments statiques/désactivés n’apparaissent qu’après décision explicite et restent accessibles, sans fausse action ou donnée inventée.
- [ ] Les styles réutilisent les composants et tokens locaux ; aucune dépendance, police distante, route, préférence, donnée persistante ou couche d’architecture n’est ajoutée.
- [ ] Les tests automatisés liés couvrent la parité du contenu, les régressions de commande et les états responsive structuraux. `npm run check`, `npm run build` et `npm run verify:build` réussissent ; la CI indépendante est verte sur le SHA final.

## Implementation constraints
Respecter `AGENTS.md`, les spécifications canoniques, la frontière entre le shell, Overview et le détail projet ainsi que les interactions React livrées. Utiliser les données existantes et leurs libellés véridiques. Les décisions visuelles Stitch approuvées priment pour l’apparence ; les spécifications produit et les comportements livrés priment pour les règles et les commandes. `automation: manual` : aucune étape OpenSpec/OpenRouter payante ne démarre à la création ou à la fusion de la fiche.

## Out of scope
- Ajouter recherche, filtrage par état, tri, échéances, partage, archivage, pièces jointes, activité, identifiant/code projet, description projet, couverture/image, données d’espace ou de stockage qui ne font pas partie du contrat actuel.
- Ajouter ou changer un modèle de données, une persistance, une règle de calcul, une route, une commande, une synchronisation, une règle de sécurité ou un comportement produit.
- Remplacer les données réelles par des placeholders trompeurs ou présenter un contrôle désactivé comme une fonction disponible.
- Refaire le shell, les quatre destinations de navigation, l’architecture générale React ou les tokens globaux.

## Assumptions or decisions
Les maquettes Stitch sont déjà approuvées comme références visuelles et UX, sur mobile et desktop ; aucune nouvelle approbation de maquette n’est requise. L’inspection des cartes desktop confirme cependant des commandes et métadonnées qui ne sont pas dans le produit actuel. Avant que la tâche soit exécutable, le propriétaire doit choisir le traitement de ces groupes : (1) recherche, filtres d’état et tri ; (2) échéances/calendar ; (3) description, catégorie/code, couverture et métadonnées du projet ; (4) partage et archivage ; (5) panneau latéral de prochaine action, progression et activité du projet. Les options sont de les exclure de l’harmonisation, de créer des tâches fonctionnelles distinctes, ou d’autoriser un traitement visuel statique/désactivé limité. Il n’est pas nécessaire de décider ici qu’un ADR doit changer ; réviser l’ADR uniquement si le plan OpenSpec révèle une contradiction concrète.

## Manual acceptance
Vérifier visuellement les cartes sur desktop et téléphone aux largeurs représentatives. Parcourir les commandes existantes au clavier et au toucher ; contrôler les sous-tâches, le focus visible, les libellés longs, le défilement et la continuité des formulaires. Consigner séparément toute recette réellement effectuée ; les tests automatisés ne constituent pas une recette physique.

## Post-sync review
Examiner le diff sémantique et les spécifications mises à jour, la CI indépendante sur le SHA exact, l’archivage OpenSpec, la CI sur main et le déploiement Pages.
