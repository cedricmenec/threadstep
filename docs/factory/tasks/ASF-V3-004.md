## Objectif fonctionnel

Préparer une interface technique entre le manifeste/journal V3, la preuve de provenance GitHub et une mise à jour CAS, **sans** disposer d'un token d'écriture, sans activer de workflow, sans revendication payante réelle. La tâche doit démontrer en simulation qu'un child run ne peut obtenir qu'**un checkpoint unique CLAIM_CHILD** et qu'un autre contrôleur ne peut être attaché qu'à un checkpoint nominal vérifié.

## Réalisation proposée

- [x] Créer un adaptateur GitHub **lecture seule** qui lit `manifest.json` et `journal.json` à la **même référence SHA de commit** sur `asf/waves/<waveId>`.
- [x] Lire uniquement les deux fichiers attendus via les URLs REST GitHub prévisibles ; ne pas permettre les chemins d'utilisateur ou d'agent.
- [x] En lecture, refuser documents manquants/incomplets/surdimensionnés, ref déplacé inaccessible, manifestHash divergent, secrets apparents, validation du manifeste manquante ou rejeu du journal non concordant.
- [x] Créer un pont transactionnel `attemptV3ChildClaim` qui corrèle réservation ACK, run enfant exact, attempt=1 et provenance observée, puis ne propose `CLAIM_CHILD` à l'adaptateur CAS **qu'après validation**.
- [x] Refuser le second claim, le claim sans ACK, la tentative 2, le mauvais acteur, mauvais SHA, mauvais statut, preuve inconnue, écriture en conflit ou perdue.
- [x] Créer un pont `attemptV3ControllerAttach` qui n'autorise la continuation nominale qu'après `DELIVERED + CHECKPOINT` et sous le mandat owner d'origine, en conservant le quota.
- [x] Ajouter tests Node simulés pour lecture snapshot, manipulation de journal, réponses API indisponibles, claims concurrents, refus de doubles claims, relance non autorisée et conservation du quota.
- [x] Documenter dans la même PR la frontière de confiance, les limitations, les prérequis aux PR #69/#70 et les futurs tests GitHub non payants.

## Hors périmètre, limites et avertissements

Cette PR est **indépendante des PR #69 et #70** pour permettre une CI V1 sur main. Elle n'importe pas leurs modules en attente de revue. Les simulations utilisent des ports factices, et un test vert ne prouve ni l'identité d'un bot GitHub App, ni un vrai CAS distant, ni une revendication contre deux runners réels. Il **ne faut jamais** câbler un callback de test/validation permissive sur un workflow payant.

Aucun script n'invoque OpenRouter ni `workflow_dispatch`. Le pont retourne `checkpoint_committed` seulement après réponse simulée du port CAS ; cette réponse **ne vaut pas autorisation de payer**. L'authentification E2E et le verrou global restent manquants.

La PR #66 décrit le cycle de vie métier ; les PR #69 et #70 fournissent les contrats réels à brancher dans un lot ultérieur de revue sécurité. Les noms V3 des workflows mentionnés sont **projetés** et non activés.

Automation: manual. Aucun démarrage payant ni fusion automatique autorisés.
