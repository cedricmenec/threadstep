# ASF-V3-002 | Contrôleur V3 pur : transitions, réservation, identité enfant et continuation

Status: implementation proposed, in review (draft PR; NOT deployed)
Type: factory
Automation: manual
Priority: high
Dependencies: ASF-V3-001 (design proposal under review, PR #66)
Phase: ASF V3 / contrôleur durable
Created: 2026-10-16

## Valeur et contexte

Poser un noyau V3 **déterministe et sans effets de bord**, permettant la simulation d'une vague autorisée de 1 à 10 tâches, avec réservation avant dispatch, intention persistable, confirmation d'un run enfant, revendication unique avant paiement, preuve de livraison, checkpoint et continuation inter-runs liée au mandat initial.

La V1 opérationnelle et ses limites 1/2 ne sont **pas** modifiées. Cette PR ne publie ni contrôleur Actions ni nouvel exécuteur et ne donne pas de droits de dispatch ou de paiement.

## Périmètre d'implémentation de cette PR

- [x] Isoler un nouveau module \`scripts/asf/v3/lifecycle.mjs\` version 2, sans import susceptible d'exécuter une commande GitHub ou OpenRouter.
- [x] Valider strictement \`maxTaskStarts=1..10\`, acteurs et workflows attendus, modèle connu, source SHA et empreintes des tâches candidates.
- [x] Exposer un manifeste figé et un journal V3 immuable avec révision monotone, journal d'événements et rejeu intégral contrôlant les invariants.
- [x] Modéliser \`RESERVE → DISPATCH_INTENT → ACK_CHILD → CLAIM_CHILD → PR_PUBLISHED → DELIVERED → CHECKPOINT\` ; aucun événement de lancement réseau dans ce module.
- [x] Refuser double claim, autre run enfant, attempt 2, quota dépassé, tâche déjà tentée, mauvais ordre et nouvelle sélection après état terminal.
- [x] Exiger, pour une continuation nominale, le dernier checkpoint et des observations de l'autorisation propriétaire originelle et du nouveau contrôleur.
- [x] Faire du \`STOP_FAILED\` et du \`STOP_UNCERTAIN\` des états terminaux ; seule une note de réconciliation non payante peut y être ajoutée.
- [x] Écrire les tests de simulation, avec vague nominale de dix tâches, CI rouge, Pages rouge, refus d'un onzième, crash/dispatch incertain, CAS et replay.
- [x] Documenter contrat, frontières de confiance, lacunes non livrées et procédure de validation dans la même PR : [v3-controller-contract.md](../v3-controller-contract.md).

**Note sur les checkboxes :** les cases ci-dessus signifient que les fichiers de code/tests/documentation ont été proposés dans la branche. La validation effective des tests sera enregistrée distinctement dans la PR et/ou ici après lecture de la CI. Aucun pilote réel n'a eu lieu.

## Critères d'acceptation vérifiables avant fusion

- [ ] \`npm run check\` ou CI indépendante \`check\` réussi **sur le SHA final de la PR** ; les tests V1 continuent de réussir.
- [ ] Le nombre de départs réservés ne dépasse jamais N, pour N=1..10, même si plus de N candidates existent.
- [ ] Le code ne peut pas produire un deuxième claim payant de la même réservation ; aucun ordre réseau n'est émis par le kernel.
- [ ] Un run contrôleur inédit ne peut être attaché qu'après checkpoint et corrélation au mandat originel ; le même run ne peut pas être attaché une seconde fois.
- [ ] La réponse GitHub ambiguë est traitée comme \`STOP_UNCERTAIN\` par le futur adaptateur ; aucune auto-relance HTTP autorisée.
- [ ] Les données externes simulées sont décrites honnêtement comme des **observations à vérifier par un adaptateur sécurisé**, non des preuves GitHub authentifiées en production.
- [ ] Revue humaine du diff, du contrat et des limites avant décision de fusion.

## Hors périmètre et limites connues

- Aucun changement de \`.github/workflows/*\`, \`agent-openspec.yml\`, \`authenticate-executor.mjs\`, politique de publication, GitHub App, secrets, règles de main ou \`AGENTS.md\`.
- Pas d'API GitHub, d'appel OpenRouter, de branche opérationnelle \`asf/waves/*\` ni de run réel. La **vraie atomicité inter-runs** et la preuve GitHub vérifiée ne sont donc **pas démontrées**.
- Le registre/claim reste un modèle de données. L'adaptateur autorisé devra écrire les événements de manière atomique via une comparaison sur **le commit SHA Git distant**, non uniquement sur \`journal.revision\`.
- La version V3 \`repository_dispatch\` et le workflow \`backlog-orchestrator-v3.yml\` sont des noms de contrat projetés ; ils n'existent pas en production.
- Cette PR seule n'implémente ni le scheduler GitHub V3, ni le verrou global multi-vagues, ni une limite USD, ni la sécurité GitHub en production. Elle ne doit jamais être présentée comme une V3 exécutable.
- Les éventuelles extensions sensibles de permissions doivent passer dans une PR indépendante autorisée.
