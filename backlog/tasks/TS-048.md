# TS-048 | Rétablir les projets après une vérification de compte Cloud

## User value
Après un nouveau déploiement, un rechargement ou un événement Dexie Cloud, les projets doivent rester disponibles sans devoir réimporter un JSON, purger la copie locale, se déconnecter ou recréer une base `recovery`. Le diagnostic doit expliquer un blocage réel et ne jamais annoncer des données masquées lorsque le compte est lié.

## Incident et preuve
Le 20 octobre 2026, Android puis laptop affichent une page « Mes projets » vide malgré une session authentifiée, une base locale `threadstep-recovery-*`, la liaison du compte reconnue et une synchronisation native `in-sync`. L'utilisateur indique que la base Dexie Cloud contient les projets. La vérification directe des tables `subjects`/`items` sur ces appareils reste nécessaire.

Un chemin reproductible dans le code peut produire cet écran : `clearBusinessForBindingBlock()` réinitialise le document mais laisse `businessStarted` à `true` ; `startBusiness()` refuse alors une nouvelle lecture. Le retour de confiance par les événements natifs appelle `refreshAccountBinding()` sans reprendre le chargement métier. Une lecture IndexedDB lancée sous une ancienne identité peut également se terminer tardivement. Ces défauts sont établis par inspection et tests déterministes, mais ne constituent pas une preuve exhaustive de la cause du cas réel Android/laptop.

## Scope
- Assurer l'invariant : **compte actuellement autorisé + données non chargées = tentative de lecture/relecture**, y compris après événements natifs tardifs, rechargement et reprise de session.
- Invalider le marqueur « déjà démarré » lorsque l'accès est réellement bloqué ; ne pas effacer IndexedDB ni présumer la copie distante vide.
- Ne jamais afficher des résultats d'une lecture ancienne sous un compte ou une base devenus différents ; consolider les reprises simultanées sans boucles de rafraîchissement.
- Ne présenter les causes historiques de bootstrap comme causes possibles de blocage que lorsque la liaison est actuellement bloquante. Conserver les données du diagnostic technique sans inventer de perte ou de convergence.
- Réduire les mécanismes plutôt qu'ajouter un nouveau cache, une nouvelle migration ou un contrôle supplémentaire d'accès.

## Acceptance criteria
- [ ] Une session Dexie Cloud autorisée affiche les projets présents dans la base locale effective après connexion, reload, nouveau déploiement et événements `currentUser`/`persistedSyncState` tardifs.
- [ ] Une liaison temporairement bloquée puis restaurée reprend automatiquement la lecture métier sans réinitialisation ni OTP supplémentaire.
- [ ] Une lecture commencée sous A ne rend rien après bascule vers B ; le compte et la base effectivement autorisés sont relus.
- [ ] Aucun chemin de correction ne supprime, ne purge, ne copie, ne fusionne ni ne recrée automatiquement une IndexedDB locale ou une base distante.
- [ ] Pour une liaison `BOUND`, le diagnostic n'affiche plus « Cause indéterminée : données masquées » ; pour un blocage réel, il conserve l'information de protection.
- [ ] Les tests de régression ciblés et `npm run check` passent sur le SHA livré. La recette manuelle Android/laptop est distincte de la preuve CI.

## Manual acceptance
Sur une instance Dexie Cloud de test contenant des projets vérifiés côté service : deux appareils Chrome Android et laptop ; reload, déploiement, reprise OTP, événements de synchronisation, compte/URL A→B→A, hors ligne/retour réseau et deux onglets. Comparer les comptes `subjects`/`items` dans l'IndexedDB effective et la liste visible, sans intervention destructive. Si la copie locale est réellement vide, vérifier explicitement la récupération Cloud sans conclure que le serveur est vide. Conserver une sauvegarde avant toute opération de récupération volontaire.

## Implementation constraints
- Garder Dexie Cloud comme mécanisme natif, IndexedDB comme stockage local effectif et l'isolation des comptes TS-038/TS-045.
- Aucun secret, email, OTP, identifiant de compte brut ni donnée métier dans les traces, PR ou télémétrie.
- Maintenir le comportement mobile, les exports existants et les actions de suppression exclusivement explicites.
- Ne pas utiliser `in-sync` comme preuve de convergence des projets entre appareils.

## Out of scope
Reconcevoir Dexie Cloud, migrer les bases `threadstep-recovery-*`, supprimer les anciennes copies, transférer implicitement des projets, promettre une récupération serveur non vérifiée, ou modifier les workflows ASF.

## Assumptions or decisions
Le correctif est manuel en raison du risque élevé de masquer les projets d'un autre compte. La CI ne peut pas remplacer la recette réelle multi-appareils.
