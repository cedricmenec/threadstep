# TS-058 | Préparer une frontière d'intégration React dans ThreadStep

## User value

Préparer une migration progressive vers des composants React maintenables, sans changer l'apparence ni les usages actuels et sans exposer les données ou la synchronisation à une seconde logique applicative.

## Verified context

- Vite 7.3.7 est en place depuis TS-057 (PR #192) et le build `dist/` est publié sur GitHub Pages après ASF-WF-004 (PR #194), sous `/threadstep/`.
- `site/app.js` gère aujourd'hui l'état de présentation, les interactions, le rendu impératif et l'appel à la persistance. `render()` remplace notamment les descendants de `#subjects` ; l'intégration React dans ce même sous-arbre exige une cession explicite de propriété DOM.
- Les règles métier réutilisables vivent dans `site/core.js` ; la persistance locale et la synchronisation Dexie sont portées par des modules existants. La continuité focus/scroll/repli et l'isolation des comptes sont des contrats canoniques.
- Cadrage Notion : [UI-02, pilote React](https://app.notion.com/p/40212ac916368148b26be851a842d9f7) ; orientation initiale dans l'[étude Stitch](https://app.notion.com/p/40212ac916368166b01edb6d385b4f1d). TS-059 livrera la première surface métier React.

## Scope

1. Ajouter `react` et `react-dom` à des versions exactes compatibles avec Vite, avec lockfile reproductible et compilation locale. Choisir et documenter le traitement JSX et les exigences CSP du build de production, sans CDN ni script inline supplémentaire.
2. Définir un contrat de montage/démontage pour une **unique surface de présentation bornée**, destinée à la vue détail d'un projet dans TS-059. Le routeur/hash, les garde-fous d'accès métier et les autres surfaces restent gérés par l'application existante.
3. Rendre explicite la propriété DOM : lorsqu'une racine React est active, le renderer vanilla n'écrit jamais dans ses descendants ; avant de rendre à nouveau en vanilla, la racine est démontée. Éviter les montages cumulés et les listeners dupliqués au fil des navigations/rafraîchissements.
4. Définir un adaptateur de présentation entre le contrôleur existant et le futur composant React : snapshot métier en lecture seule, état UI transitoire clairement identifié, commandes/callbacks explicites, notification de rafraîchissement et invalidation lors d'une navigation ou d'un changement d'identité autorisée.
5. Réutiliser `site/core.js`, les identifiants, les règles de validation et le flux d'écriture existant. Aucun second store métier, aucune écriture déclenchée par un montage/rendu, aucune souscription directe de React à Dexie Cloud ou à l'OTP.
6. Ajouter une infrastructure de tests déterministes pour React et l'adaptateur, avec fixture à données synthétiques pour monter/démonter la future surface sans activer de fonctionnalité React métier en production.
7. Documenter le point de bascule réversible vers le rendu vanilla, les limites d'intégration et la procédure de diagnostic. Le contrôle de bascule ne crée ni préférence persistée, ni nouvelle route publique, ni transfert de données.

## Acceptance criteria

- [ ] `npm ci`, `npm run check`, `npm run build`, `npm run verify:build` et une prévisualisation sous `/threadstep/` fonctionnent ; les dépendances React sont verrouillées et aucun CDN, secret, assouplissement de CSP de production ou ressource au mauvais chemin n'apparaît.
- [ ] Un test d'intégration monte puis démonte la racine React, répète navigation et rafraîchissement simulés, et prouve qu'aucun descendant n'a deux propriétaires DOM ni listener actif dupliqué.
- [ ] L'adaptateur fournit les données métier en lecture seule et route les intentions via des commandes explicitement nommées du contrôleur existant ; le montage, le rendu, le démontage et une simple préférence visuelle n'émettent aucune écriture Dexie/IndexedDB ni requête Cloud.
- [ ] Une transition de route, de compte/espace non autorisé ou d'état de chargement bloquant invalide l'ancienne présentation et ne laisse voir aucune donnée du contexte précédent.
- [ ] Les tests couvrent l'absence d'une nouvelle source de vérité, l'identité stable des items et le contrat de non-régression des URLs/hash. Les tests existants restent verts et la sortie build demeure statique.
- [ ] Tant que TS-059 n'est pas appliquée, Overview, vue détail, Paramètres et Synchronisation restent visuellement et fonctionnellement identiques à la référence Vite publiée.
- [ ] Une procédure de retour arrière, la liste des fichiers concernés, les écarts de taille du build et les limites de vérification sont documentés.

## Implementation constraints

- Préférer un adaptateur étroit à une extraction générale du monolithe `site/app.js`. Ne pas réécrire `core.js`, les modules Dexie/OTP, la sauvegarde, l'import/fusion, la restauration, le consentement ni la récupération.
- Garder `site/` comme source Vite et `dist/` comme artefact ; conserver les routes `#/`, `#/sujet/:id`, les paramètres et les URLs publiques.
- Respecter `openspec/specs/ux-interaction-continuity/spec.md`, `app-navigation`, `workspace-identity-isolation`, `frontend-security-boundary` et `static-build-pipeline`.
- Ne pas modifier `AGENTS.md`, `.github/workflows/*`, les protections, secrets, permissions ou scripts ASF protégés. Toute évolution nécessaire de la factory serait une tâche/PR ASF distincte.
- `risk: medium`, `automation: manual` : les frontières DOM et les conditions d'invalidation doivent être revues avant le pilote ; aucun lancement OpenRouter/OpenSpec n'est autorisé par la création de la fiche.

## Manual acceptance

Sur le build Vite et un profil de test desktop/Chrome Android, vérifier que les écrans existants, la navigation, le focus et le scroll sont inchangés ; vérifier avec les outils réseau qu'aucune requête Cloud supplémentaire n'est provoquée par l'outillage. Ces observations ne sont pas attestées par la seule CI et ne doivent pas être cochées rétroactivement.

## Post-sync review

Comparer le diff et les specs synchronisées, inspecter le build, la CSP et le graphe de dépendances, confirmer la CI indépendante au SHA de PR puis sur `main`, et conserver une preuve explicite des vérifications manuelles réellement réalisées. Ne pas considérer le socle comme une migration de vue achevée.

## Out of scope

Migration visible des tâches et du détail projet (TS-059), React sur Overview, navigation ou Paramètres, parcours Dexie Cloud, Tailwind, design system, maquettes Stitch, nouvelles fonctionnalités, migration de données, changement de workflow Pages/CI, activation payante ou déploiement de nouvelle UI.

## Assumptions or decisions

- La première surface cible est **le détail d'un seul projet**, pas l'Overview multi-cartes. TS-059 confirmera l'interface exacte de l'adaptateur par ses tests de comportement.
- Les composants React de production ne sont pas activés par cette tâche ; seule une fixture de test vérifie le montage. Une seconde source de persistance ou une coexistence DOM concurrente est explicitement interdite.
- La décision Tailwind/CSS reste différée ; les styles existants restent la référence.
