## Architecture livrée avec cette PR

- Une entrée `workflow_call` permet à un seul appelant sur `main`, `.github/workflows/backlog-orchestrator.yml`, de réutiliser le moteur OpenSpec existant. Le contexte GitHub reste celui du workflow appelant.
- Le précontrôle vérifie `wave_id`, `parent_run_id`, `reservation_sha`, la provenance du run parent lancé par le propriétaire, son état en cours, le manifeste immuable, la réservation `DISPATCH_RESERVED` et l'empreinte du brief de tâche à son SHA source.
- Contrat du stockage de vague pour 009 : branche `refs/heads/asf/waves/<wave_id>`, fichiers `manifest.json` et `journal.json`, `reservation_sha` égal au SHA exact de la pointe de branche au moment du démarrage de l'exécuteur. Toute modification concurrente provoque un arrêt.
- Les trois exécuteurs payants partagent `threadstep-paid-development-v1` à l'échelle des **jobs**. Le parent qui attend n'acquiert pas ce verrou. En l'absence de support de la nouvelle option `queue: max` par la version d'Actionlint épinglée, GitHub peut remplacer une exécution en attente ; toute annulation doit être traitée comme arrêt/reprise contrôlée, jamais comme retry payant automatique.
- Le jeton GitHub Actions natif d'OpenSpec est limité à `contents: read` dans son job d'exécution ; seul son jeton App existant crée les branches et PR. Aucun secret ou droit App n'est modifié.
- La tâche 009 devra utiliser l'appel de workflow réutilisable et le journal à réservation durable, corréler ses jobs avec le run parent, puis vérifier la livraison complète. Le fait de fusionner 008 **ne déclenche aucun modèle payant** ni nouvelle vague.
