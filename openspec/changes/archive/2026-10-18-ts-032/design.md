# Design

## Context

See `proposal.md` — Why.

The delivered code has two persistence paths:

- `site/app.js` uses `localStorage` (`threadstep.document.v1`) when no valid
  Cloud URL is registered, and a Dexie/IndexedDB store when one is.
- `site/dexie-foundation.js` exposes `dexieSchema()` for the synchronized
  `threadstep` database, and `bootstrapSyncedDatabase()` constructs it with the
  `dexieCloud` addon only behind a valid URL.
- `site/persistence.js` already provides V1 ↔ records projection, fine-grained
  mutation planners, local error kinds, an injectable `commit(operations)`
  contract and a compatibility guard.
- `site/synced-records.js` provides a fail-closed validated read of the
  `subjects`/`items` tables, currently used after OTP authentication.
- `site/local-recovery.js` returns a frozen, byte-for-byte historical V1 JSON
  export without opening IndexedDB or authenticating.
- Existing tests assert that the synchronized bootstrap stays behind the Cloud
  URL gate, that no `++id` is used and that the historical key is never removed.
  Those tests describe the current historical path and must be updated to the
  local-first target without weakening the Cloud guarantees.

The runner has no DOM or real IndexedDB. Logic that must be proven must therefore
be pure/injectable or statically assertable; the real browser behavior remains
manual acceptance.

## Goals / Non-Goals

**Goals:**

- Open an autonomous local Dexie workspace on first launch with no URL, OTP,
  Cloud addon or network.
- Keep every local business mutation, import and export on that transactional
  workspace, with confirmation only after commit.
- Keep local records physically separate from any synchronized workspace before
  TS-037 consent.
- Preserve the historical V1 key and expose its existing export without an
  automatic conversion.
- Make the business view available without a Cloud identity.
- Preserve the existing synchronized workspace and OTP path when a valid URL is
  already configured.
- Cover deterministic behavior with runner tests and static assertions.

**Non-Goals:**

- Implementing TS-033 conversion, TS-037 activation, remote pull/push or OTP.
- Changing the V1 data model, quotas, domain rules or navigation.
- Adding a browser test framework, `fake-indexeddb`, jsdom or a new dependency.
- Removing or rewriting historical archives, factory files or workflows.

## Decisions

### 1. Two stable workspaces, not one shared database name

The autonomous local workspace uses a dedicated stable database name
(`threadstep-local` proposed) with the same schema version, `subjects`/`items`
stores and string primary keys as the synchronized schema. It is opened by a
plain `new Dexie(name)` with no `dexieCloud` addon and no
`db.cloud.configure()`.

The synchronized workspace keeps the existing `threadstep` name, schema and
native `nameSuffix`. A valid stored Cloud URL therefore selects a different
IndexedDB database, and no local record becomes eligible for replication merely
because the user later enters a URL.

Alternatives considered:

- **Reuse `threadstep` for both modes.** Rejected: configuring the addon on a
  database that already contains local records creates a real pre-consent push
  risk and contradicts the target isolation rule.
- **Keep local data in `localStorage` until TS-037.** Rejected: TS-032 requires
  IndexedDB as the default business store and a durable transactional write
  path.
- **Use a separate non-synchronized table inside `threadstep`.** Rejected for
  this step: Dexie Cloud's exact table eligibility is version/service dependent;
  a physically separate database gives a simpler, provable isolation boundary.

The name is a design proposal, not a product requirement. The stable requirement
is that local and synchronized names stay stable and distinct.

### 2. Reuse the existing schema and identity conventions

`dexie-foundation.js` gains a local schema/bootstrap descriptor derived from the
same explicit version and store definitions:

- database name: dedicated local name;
- version: the existing explicit integer schema version;
- stores: `subjects: "id"`, `items: "id"`;
- upgrade: the existing non-destructive upgrade hook;
- identifiers: UUID or `legacy:` strings generated by the existing planners,
  with no `++id`.

This keeps future TS-037 records compatible with the synchronized schema while
proving that local mode itself never opens a synchronized instance.

### 3. One transactional store adapter for both modes

Move/refactor the current `createBusinessStore(db)` into
`site/persistence.js` as an injected Dexie-adapter factory (for example
`createDexieStore(db)`), using one `readwrite` transaction over `subjects` and
`items`. Both the local and synchronized databases use it.

Local `load()`, `persist()`, import and export stop using the business
`localStorage` key:

- `load()` reads validated records from the local database transaction, then
  projects them with `recordsToDocument`.
- `persist()` diffs the previous records against the next document, commits the
  operation set in one transaction, and only then updates `lastRecords`, the
  visible state and the status message.
- Local import validates the complete V1 document and commits one atomic
  operation set after confirmation.
- Export serializes the committed projection (`recordsToDocument`) to V1 JSON,
  never reads `localStorage`.

The existing resume preference (`threadstep.resume.v1`) remains origin-local
`localStorage` and is never written to IndexedDB or exported.

### 4. Startup and visibility without Cloud identity

Startup will branch explicitly:

- If a valid Cloud configuration exists, keep the delivered synchronized
  bootstrap, authentication controller and gated Cloud workspace.
- Otherwise, create the local database and business store, set the business
  view visible, subscribe to multi-tab changes, load IndexedDB and render. Do
  not create an auth controller, do not call `db.cloud`, and do not render the
  OTP panel as a prerequisite.

`requiresAuthentication()` remains tied only to the synchronized workspace.
`applyBusinessVisibility()` must not hide the local dashboard while IndexedDB
loads and must show the local loading/error status instead.

### 5. Fail closed on local storage problems

Local open, read and commit errors are first-class states:

- `open` failure: show an explicit local persistence error, hide no historical
  export and do not fall back to `localStorage` as a business store.
- `read` failure: keep the last known state, show an error and do not render an
  empty dashboard as if it were authoritative.
- `commit` failure: do not update the confirmed projection, do not announce
  success, restore the last committed view, show a local error distinct from a
  Cloud/network error and block further writes until recovery/reload.

The existing `localError`/`isLocalError`/`syncError` distinction is reused. No
local failure may be reported as a successful save or as a remote sync issue.

### 6. Legacy V1 preservation is a read-only transition in TS-032

When the local workspace opens and `threadstep.document.v1` exists and parses:

- the key is never removed, renamed, rewritten or hidden;
- a visible, accessible notice reports that historical data exists and remains
  exportable;
- the existing `availableLocalBackup(localStorage)` export button is reused or
  exposed in the local view;
- no automatic import, conversion, normalization or Cloud transfer occurs.

The actual conversion remains TS-033. The notice may explain that a separate
explicit conversion will be proposed, without exposing a migration control that
does not exist yet.

### 7. Existing synchronized path stays intact

TS-032 does not remove or rewrite the delivered Cloud configuration, OTP or
reconciliation code. If a valid URL is stored, the application continues to
open the synchronized workspace and require its native session as before. The
new local workspace is a different database, so configuring a URL cannot attach
or upload the local records. A visible notice should make this separation
explicit when relevant.

## Risks / Trade-offs

- **Distinct database name changes later consolidation.** TS-037 must copy the
  consented local workspace into the synchronized workspace through the
  reconciliation plan. Mitigation: use the same schema/identifiers and document
  the boundary now.
- **Existing local users see a new empty local workspace.** Their V1 data stays
  in `localStorage` until TS-033. Mitigation: persistent legacy notice and
  byte-for-byte export; no destructive cleanup.
- **Two notices (local storage status and Cloud separation) can clutter the
  view.** Mitigation: semantic, low-noise notices with `role="status"`/`alert`,
  no OTP gate and no modal.
- **A URL form still exists in local mode.** Mitigation: keep the local and
  synchronized workspaces separate, state that local data is not transferred,
  and leave activation to TS-037.
- **Runner cannot prove real IndexedDB, offline mode or browser accessibility.**
  Mitigation: pure/fake adapter tests, static source assertions, and explicit
  manual acceptance in `tasks.md`.
- **Schema evolution on local and synchronized stores can diverge.** Mitigation:
  derive both from one versioned definition and test upgrades do not delete
  data; synchronized-store migrations remain subject to Dexie Cloud rules.

## Migration Plan

1. Ship TS-032 with no automatic migration. Existing `threadstep.document.v1`
   remains untouched and exportable; the new local workspace may start empty.
2. Existing users with a valid stored Cloud URL keep their synchronized
   workspace; no database is renamed or deleted.
3. Rollback consists of reverting the application code: the local IndexedDB
   workspace may remain but is ignored by the previous release, and the
   historical `localStorage` key is still intact.
4. TS-033 later performs the explicit, idempotent V1 → local conversion; TS-037
   later performs the consented local → synchronized transfer. Neither is
   implemented here.

## Open Questions

None that would change the specs or the task breakdown. The local database name,
notice wording and final placement are implementation details recorded as
uncertainties in `proposal.md`; they do not change the required behavior.
