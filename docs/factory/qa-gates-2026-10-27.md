# ASF-QA-01 | Des contrôles simples, placés au bon moment

**Audit du 27 octobre 2026.** Périmètre : workflow OpenSpec, CI indépendante et tests existants du dépôt `cedricmenec/threadstep`. Cette synthèse décrit la modification proposée dans la PR ASF-QA-01, et non une réussite encore présumée de cette PR.

## Décision de conception : keep it simple

Questionner d'abord l'utilité de chaque contrôle, **supprimer les répétitions équivalentes**, puis simplifier le diagnostic. Ne pas ajouter d'orchestrateur, cache de résultats, mécanisme de retry, seuil de tests ignorés, dépendance de reporting ou appel LLM supplémentaire. Conserver le principe **fail closed** pour tous les contrôles importants.

## Inventaire des suites

L'inventaire GitHub de `tests/*.test.mjs` sur `main` avant ASF-QA-01 comprend **120 fichiers de test** (le nombre de sous-tests Node est supérieur). Répartition exhaustive par règle de nommage, appliquée dans cet ordre, en évitant les doubles comptes :

| Famille de fichiers | Fichiers | Responsabilité première |
| --- | ---: | --- |
| `ts-065-*` | 6 | Interactions React Overview, glisser-déposer, éditeurs, isolation |
| `ts-064-*` | 9 | Cartes React Overview et dépendance/recette |
| `ts-060-*` à `ts-063-*` | 16 | Régression React détail, primitives et navigation |
| `ts-050-*` à `ts-059-*` | 24 | Continuité UI, diagnostics et premières intégrations React |
| Autres `ts-*` | 18 | Capacités historiques, UX, persistance, migrations et compatibilité |
| `agent-*`, `asf-*`, `factory-*`, `workflow-*`, `opsx-*`, `checklist-*` | 23 | Factory, workflows, politique et sécurité |
| `backlog-*` | 2 | Contrat et migrations du backlog |
| Autres `*.test.mjs` | 22 | Domaine métier, infrastructure, persistance, outils transversaux |

**Attention :** c'est une classification de couverture par noms, pas une preuve qu'un fichier ne possède qu'un seul type de test. La suite complète est conservée telle quelle ; des suites de persistance peuvent aussi tester la sécurité.

Points de fragilité observés et vérifiables :
- **Dépendance au worktree Git** : `ts-040-openspec`, `ts-058-react-docs`, `ts-059-project-detail-docs`, `ts-060-qualification-report`, `ts-064-overview-side-effects`. Elles sont valides sur un état Git stabilisé mais rejettent les specs/archives autorisées encore non committées (incident TS-064).
- **Historique Git superficiel** : `ts-065-overview-docs` exigeait initialement un commit ancêtre non accessible dans le checkout CI superficiel. Correctif TS-065 livré : attestation incluse dans HEAD en mode shallow.
- **React et jsdom asynchrones** : `ts-060-project-detail-transitions` et `ts-065-overview-continuity` ont produit `window is not defined` après la fermeture du faux navigateur. Leur traitement correct consiste à attendre/démonter les tâches React, pas à ignorer un test.
- **Validations documentaires de l'archive** : les tests utilisant des chemins OpenSpec dépendent de la phase ; OpenSpec doit d'abord déplacer la change puis la CI teste le commit final.

## Contrat de chaque phase

| Phase | Vérifications conservées / déléguées |
| --- | --- |
| `plan` | Plan/proposal/design/deltas présents, checklist techniquement exécutable, OpenSpec strict, checkpoint de plan limité à la change. La suite produit n'est plus relancée sans changement de code. |
| `apply` | L'agent teste les modules modifiés, puis **une suite complète `npm run check` obligatoire** au checkpoint d'implémentation, checklist et contrôle de portée avant push de sauvegarde. |
| `pre-sync` | La validation de la change et des cases achevées reste obligatoire. En `apply/auto`, la suite complète vient de passer au checkpoint ; pas de répétition. En `finalize` dans un nouveau runner, une suite complète requalifie le checkpoint avant le nouvel appel OpenRouter payant. |
| `opsx:sync` | Garde-fou de comparaison octet par octet `sync-guard`, changement limité aux `openspec/specs/`, validation canonique stricte **avant** archive. |
| `archive` | Archive native sans second merge, vérification de présence et validation canonique + archives strictes. |
| `publish` | Contrôle de portée depuis le vérificateur **de confiance chargé depuis `main`**, avant et après `git add -A`, commit local final et worktree propre avant push ; pas de suite complète supplémentaire. |
| **PR CI `check`** | **Suite complète obligatoire sur le HEAD réel**, actionlint, `npm ci`, build Vite, contrôle d'artefact/serveur, installation épinglée OpenCode sans modèle, validation OpenSpec stricte. Une CI rouge empêche la fusion protégée. |
| `main` / Pages | CI et publication indépendantes après fusion ; les recettes humaines desktop/Android restent explicitement séparées des tests automatisés. |

### Réduction des exécutions complètes

**Sans compter les tests que l'agent peut exécuter lui-même pendant son appel**, l'ancien workflow lançait `npm run check` quatre fois lors d'un `auto` : validation du plan, checkpoint d'implémentation, pré-sync, avant push final. Il le lançait ensuite dans la CI indépendante sur PR, puis dans la CI sur `main` et dans le job de validation Pages.

Le workflow simplifié le lance **une seule fois dans son propre `auto/apply`**, après implémentation et avant checkpoint, puis dans la CI indépendante de la PR et la vérification post-fusion. `finalize` conserve une vérification complète avant son appel payant, car il reprend sur un runner distinct.

### Compromis explicite

Une référence obsolète à un fichier OpenSpec déplacé peut désormais produire une **PR rouge**, plutôt qu'un échec avant publication (incident TS-063). Ce n'est pas une livraison : la CI indépendante est toujours bloquante. Ce compromis rend le problème visible et corrigeable dans une PR, sans recalculer tous les tests pendant la synchronisation sémantique. Aucun chemin sensible n'est autorisé de plus ; le modèle ne peut ni fusionner une PR rouge ni lever Protect Main.

## Messages d'erreur lisibles

La CI conserve le journal complet et son statut bloquant, mais son `GITHUB_STEP_SUMMARY` affiche uniquement, en cas d'échec, les titres `not ok` de Node TAP (maximum dix), leurs lignes `error:` et le total `# tests / # pass / # fail`. Si une commande hors TAP échoue, elle affiche la fin du journal. Si aucune sortie n'a pu être produite, elle signale que l'échec se situe plus tôt dans le job. Il n'y a ni nouveau service ni nouvelle dépendance.

Scénarios de non-régression : `tests/asf-qa-01-summary.test.mjs` vérifie un échec React simulé, un échec `backlog:check` et un journal absent. `tests/asf-openspec-postarchive-order.test.mjs` protège les ordres de sync, archivage, commit, contrôle de portée et CI. Le `pipefail` CI garantit qu'une commande `npm run check` rouge reste rouge même si `tee` réussit.

## Mesure avant changement

Sur les **22 derniers runs CI terminés** accessibles lors de l'audit (25 au 27 octobre 2026), **19 ont réussi et 3 ont échoué**. Ce sont des échecs réels de code ou de tests historiques, **pas** une fréquence statistique de flakiness établie. La durée totale observée, de création à mise à jour du run, inclut aussi orchestration et attente : échantillons CI réussis `#40425138934` (51 s), `#40425762600` (69 s), `#40425946442` (74 s). Ce ne sont pas des mesures chronométrées de `npm run check` seul.

Les incidents à rapprocher : [TS-064 #40413844910](https://github.com/cedricmenec/threadstep/actions/runs/40413844910), [TS-065 #40423070296](https://github.com/cedricmenec/threadstep/actions/runs/40423070296), [PR TS-065 rouge #40424921061](https://github.com/cedricmenec/threadstep/actions/runs/40424921061). Un diagnostic de stabilité nécessite davantage d'exécutions indépendantes non payantes avant d'identifier un test comme intrinsèquement intermittent.

## Non-objectifs et acceptation

- Pas de suppression des 120 suites existantes ; aucun `skip`, `continue-on-error`, contournement de règles GitHub, modification de secrets, permissions, provider/modèle, tarification ou produit.
- Pas de rafale de CI répétées pour simuler artificiellement une stabilité ; seulement la CI provoquée par la PR normale.
- Pas d'attestation de recette humaine ni de disponibilité Cloud déduite de la CI.
- La CI sur PR valide la syntaxe des workflows et les tests sur son SHA, mais seule une vraie future exécution OpenSpec permet de confirmer toutes les phases sur runner payant.
