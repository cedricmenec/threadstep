# ASF-V3-003 | Provenance GitHub et persistance CAS inter-runs (adaptateurs isolés)

Status: implementation proposed, draft PR for separate human review; NOT deployed
Type: factory
Automation: manual
Priority: high
Dependencies: ASF-V3-001 (PR #66) and ASF-V3-002 (PR #69), both still under review
Phase: ASF V3 / sécurité des runs et journal
Created: 2026-10-16

## Objectif métier

Rendre les règles de sécurité du futur contrôleur V3 suffisamment testables pour qu'une vague de dix tâches puisse être répartie entre plusieurs runs sans jamais confondre une identité de run déclarée avec une identité observée sur GitHub, ni écraser un journal concurrent.

**Cette PR est volontairement indépendante du code encore en revue de ASF-V3-002** : elle importe seulement les utilitaires V1 stables, et expose des adaptateurs que l'intégration V3 pourra utiliser après validation des prérequis.

## Périmètre de cette PR

- [x] Ajouter `scripts/asf/v3/provenance.mjs`, un vérificateur de **métadonnées observées en lecture seule** par API GitHub : mandat initial propriétaire, chemin et événement du workflow, actor, repo, ref `main`, SHA, run ID et attempt=1.
- [x] Distinguer les runs enfants via `workflow_dispatch` et les runs contrôleurs de continuation via `repository_dispatch`, avec contrôle explicite de l'identité du bot attendue.
- [x] Rejeter les contextes incohérents avant toute lecture et retourner `uncertain` lorsque GitHub ne fournit pas de preuve complète, sans déduire une autorisation du seul JSON de contexte.
- [x] Ajouter `scripts/asf/v3/git-cas.mjs`, un port Git de persistance de journal qui crée un commit à **parent unique = ancien HEAD attendu**, et met à jour le ref **sans force**.
- [x] Refuser avant toute écriture un journal de mauvaise version, qui ne passe pas son vérificateur injecté, trop volumineux ou contenant des valeurs ressemblant à des secrets.
- [x] Refuser une écriture concurrente de ref et traiter un résultat réseau ambigu comme `uncertain`, **sans aucun retry implicite**.
- [x] Ajouter `tests/asf-v3-provenance-cas.test.mjs` : fake GitHub transport, identité correcte et usurpée, absence de réponse, deux writers concurrents, ref déplacé, erreur après écriture et cas de journaux suspects.
- [x] Ajouter dans cette même PR le document de sécurité et d'exploitation `docs/factory/v3-provenance-cas.md` : contrat des ports, preuves, permissions attendues, contraintes de migration et limites.

Les cases attestent de la **préparation des fichiers** dans la PR, pas de l'intégration réelle aux workflows.

## Critères de revue avant fusion

- [ ] `npm run check` + actionlint/CI indépendante `check` réussis sur le SHA final ; conserver tous les tests V1 au vert.
- [ ] Les tests de provenance interrogent exclusivement des runs GitHub par **ID exact** et bloquent parent/child/continuation discordants.
- [ ] Le test de concurrence prouve qu'une seule écriture `force:false` réussit pour deux commits frères basés sur un même HEAD simulé.
- [ ] Ni erreur réseau ni confirmation ambiguë ne provoquent une seconde mise à jour automatique du journal.
- [ ] Aucune modification de `.github/workflows/`, de secrets, de permissions App, de la policy agent ou de `main`.
- [ ] Contrat de confiance relu par humain avant futur raccordement au modèle payant.

## Limitations fermes et hors périmètre

- L'adaptateur de provenance **ne suffit PAS** à autoriser OpenRouter. Il ne valide pas un manifeste V3 signé ou issu du dépôt de référence ; n'effectue pas un claim V3 atomique ; n'établit pas encore la corrélation cryptographique du payload de dispatch. Son résultat est une **observation** qui doit être combinée au journal validé de ASF-V3-002 et au mécanisme de claim dans une PR ultérieure.
- Le port CAS est **injecté** et uniquement simulé ici. L'adaptateur GitHub REST/CLI réellement privilégié, la validation de la branche et le rôle de publication devront être examinés dans une PR sensible indépendante avant exécution.
- L'identité bot `threadstep-software-factory[bot]` est une hypothèse attendue de la connexion App ; sa valeur doit être confirmée en vrai sur les futurs runs V3, sans desserrer les contrôles de provenance en cas d'écart.
- Pas de dispatch, pas de GitHub token d'écriture, aucune modification de workflows, aucun appel OpenRouter, aucun merge et **aucune activation V3**.
- La création d'une PR de revue ne vaut ni autorisation payante, ni autorisation d'élargir les droits App.

## Revue post-PR

Revoir la provenance et le CAS avec l'équipe, vérifier les tests réellement exécutés, puis décider explicitement du lot d'intégration V3 qui fera le raccordement `journal V3 → Git ref CAS → GitHub run evidence → claim payant`. Fusion humaine et protections de main uniquement après revue distincte.
