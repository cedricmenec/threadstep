## Valeur fonctionnelle

Empêcher que deux vagues ASF V3 distinctes possèdent simultanément un mandat d'exécution active, y compris lorsque les runners GitHub se chevauchent. Préserver en outre l'exclusivité de la section critique **payante** déjà utilisée par V1. Ne jamais transformer une vague au statut ambigu en une nouvelle autorisation de paiement.

Une admission globale de vague est **distincte** d'un verrou de job payant : le premier évite deux ordonnancements métier actifs ; le second empêche plusieurs agents de développer simultanément. Aucun de ces mécanismes ne suffit à lui seul pour une exécution V3 sûre.

## Fichiers du lot

- \`scripts/asf/v3/global-admission.mjs\` : machine à états pure d'un **registre global** append-only, destinée à un seul ref Git \`asf/control/active-wave-v3\` commun à toutes les vagues. États \`AVAILABLE\`, \`ACTIVE\`, \`QUARANTINED\` ; événements \`ADMIT\`, \`RELEASE\`, \`QUARANTINE\`, \`DIAGNOSTIC_NOTE\`. Un waveId réutilisé est toujours refusé.
- \`scripts/asf/v3/paid-mutex-audit.mjs\` : audit de l'inventaire **exhaustif** des workflows, localisation des jobs contenant \`OPENROUTER_API_KEY\`, contrôle du mutex partagé exact \`threadstep-paid-development-v1\`, au **niveau job**, et de \`cancel-in-progress: false\`. Vérification statique d'un futur job V3 proposé.
- \`scripts/asf/v3/bootstrap-evidence.mjs\` : comparaison conservatrice d'un manifeste V3, d'un run owner réellement observé et du commit Git initial. **Ne donne jamais l'autorisation de payer**, car la signature/ancre indépendante de création de branche n'existe pas encore.
- \`tests/asf-v3-admission-mutex.test.mjs\` : concurrence logique, quotas, fin nominale, quarantaine, rejeu, manipulation de journal, audit réel des workflows présents, mutations négatives des verrous et origine non authentifiée.
- \`docs/factory/v3-admission-global-lock.md\` : présent protocole métier et technique détaillé, risques, décisions et qualification.

## Critères de réussite de la PR

- [x] Le modèle pur refuse deux admissions \`ACTIVE\` simultanées et une seconde admission du même \`waveId\`.
- [x] La sortie de quarantaine n'est **pas** automatisée : diagnostic append-only uniquement, blocage d'autres vagues tant que le propriétaire n'a pas décidé d'un protocole séparé.
- [x] Une fin nominale peut libérer le registre **uniquement** avec une preuve de journal terminal validée (injection d'une preuve structurelle dans ce prototype ; l'authentification réelle reste à ajouter).
- [x] La concurrence de deux régistres locaux n'est **pas** présentée comme un CAS distribué ; la branche Git globale nécessitera son propre CAS non forcé au HEAD, en PR séparée.
- [x] L'audit du mutex s'appuie sur les workflows du dépôt présents lors de la CI ; les jobs payants V1 sont contrôlés.
- [x] Un futur job payant V3 est rejeté si son mutex diffère de V1, si \`cancel-in-progress\` est true, ou si le preflight de claim, d'admission ou de runAttempt=1 manque.
- [x] Le contrôle du manifeste originel conserve le statut \`CONSISTENT_BUT_UNANCHORED\` même si les métadonnées concordent : preuve GitHub App indépendante nécessaire avant activation.
- [ ] CI indépendante \`check\` sur SHA final réussie, tests V1 sans régression.
- [ ] Revue humaine du contrat, de la branche globale, du mécanisme de déclenchement, du registre protégé et des conditions d'une libération après incident.

## Hors périmètre et décisions non encore autorisées

Aucun nouveau workflow, secret, GitHub App, permission ou tâche payante. Pas de création du ref global, pas de branche de vague opérationnelle et pas de dispatch. \`RELEASE\` n'est pas appelé par un vrai scheduler ; la vérification indépendante du journal terminal est un travail d'intégration futur. Le registre \`QUARANTINED\` reste bloqué ; une purge/reprise éventuelle nécessitera un acte du propriétaire et une conception séparée.

**Attention :** GitHub Actions concurrency permet un seul job en cours par groupe, mais sa politique de file d'attente peut annuler un job \`pending\` précédent. Même avec \`cancel-in-progress: false\`, aucune garantie de file FIFO durable de dix tâches ne peut être en déduite. Un job annulé après réservation doit produire un arrêt ou une incertitude, jamais un retry payant automatique.

Aucun merge et aucun run OpenRouter ne sont autorisés par cette tâche. Revue obligatoire selon AGENTS.md.
